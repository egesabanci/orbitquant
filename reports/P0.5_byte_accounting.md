# P0.5 — True Byte Accounting and Deployability Score

**Status:** Implemented and benchmarked (pure NumPy, no model/GPU).
**Files:** `baseline/p05_accounting.py`, `baseline/run_p05.py`,
`tests/test_p05_accounting.py`
**Run:** `python3 -m baseline.run_p05 --d 64 --n 8192`

## Purpose

Every experiment must report **paid bytes per token**, not nominal bits per
coordinate. Several methods look equivalent at nominal bits but diverge once
side information, residual windows, uncompressed sinks, and kernel friction are
counted (proposals.md). This is the P0.5 discipline: count quantized payloads,
packed-bit padding, norms, radii, residual norms, clip scales, zero points,
codebook IDs, protected-token pools, predictor weights, and layout metadata —
and assign a deployability score before promoting any representation.

## Method

`Representation` describes a codec's per-token costs. `accounting()` computes:
- payload bits (per-coordinate code indices × d);
- packing padding (index bits rounded up to whole bytes per block);
- per-block zero point + scale (when present, e.g. KIVI-style);
- side info (norms/radii/residual norms in the P1.3 8-bit log format, codebook
  IDs, layout);
- protected-pool metadata (1 bit/token membership flag + frac×extra bits per
  token — per-token, NOT growing with cache length);
- predictor weights (P2.10, amortized over cached tokens — the only cost that
  legitimately shrinks per token as the cache grows).

`deployability()` scores 5 properties: paged-cache fit, register dequantization,
fused-attention support, query batching, no dequantized K/V materialization.

## Findings

1. **The overheads are small but real for TurboQuant-family methods.** At 2
   nominal b/coord: TurboQuant_mse costs 2.125 true (1.06×, the 8-bit norm
   header), TurboQuant_prod 2.250 (1.12×, key norm + residual norm). QJL at 1
   nominal costs 1.125 (1.12×). These are the per-token side-information costs
   that P1.3's 8-bit log format keeps small — the exact reason P1.3 matters.

2. **Byte-packing padding is visible for PolarQuant** (3.875 nominal → 4.000
   true: 62-bit blocks pack into 64-bit bytes, +2 bits/16 coords). The paper's
   figure already includes the radius; with P1.3's 8-bit log radius it would
   drop to ~3.375 true. This is a concrete example of "looks equivalent at
   nominal bits, diverges when counted."

3. **Protected pools are cheap when accounted correctly.** 5% pool at +8
   bits/protected token costs 1.4 b/token (0.4 extra + 1 membership bit) →
   2.147 true. The earlier (buggy) version charged frac×n_tokens×extra and
   reported a nonsensical 54.3 b/coord — the regression test now guards this.

4. **Predictor weights amortize away** (64-bit scalar predictor: 0.008 b/token
   at 8192 tokens — negligible, confirming P2.10's accounting is friendly).

5. **Deployability separates the methods on verified structure, with GPU
   assumptions flagged.** TurboQuant-family and QJL representations verify 1.00
   on the three structural properties (paged-cache fit, register dequant, query
   batching — all follow from having no per-block constants). Fused attention
   and no-dequant materialization are marked **assumed**, not verified: the
   P2.1 kernels were deferred to the GPU box, so those flags are structural
   plausibility only. The KIVI-style per-block baseline verifies 0.67
   (register dequant fails) — the per-block scale must be read from memory,
   which is the systems argument for constant-free representations, but the
   full fused-path penalty is a GPU-box measurement, not a claim made here.

## Implications

- P0.5 is the measurement instrument every later proposal must report through:
  paid bytes/token, not nominal bits.
- The TurboQuant-family overhead is ~6-12% (side info), manageable and
  reducible via P1.3 (8-bit log side info) — validated here.
- Per-block-constant methods (KIVI-style) carry both a byte overhead and a
  deployability penalty (0.40 score) — a strong systems argument for
  constant-free representations.
- Protected pools (P1.5), predictor weights (P2.10), and adaptive allocation
  metadata (P2.6) are all counted: pools and predictors are cheap, per-vector
  allocation patterns are not (see P2.6 report).

## Regression tests

`tests/test_p05_accounting.py` guards: payload+side accounting, the
protected-pool per-token cost (must NOT grow with n_tokens — the bug that once
produced 54.3 b/coord), predictor amortization, and the deployability score.
